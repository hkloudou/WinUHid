# HTTP 参考程序：用网址操作虚拟键盘鼠标

`winuhid-http.exe` 启动时创建虚拟键盘和鼠标，运行期间用网址驱动它们，退出时移除。
基于同目录上一级的 `vhid` 包，不需要任何 DLL，目标机器只要装了驱动。

## 边界（必读）

**这个程序只用于可行性验证和学习。不允许原样分发给用户，也不允许部署在用户的机器或生产环境上。**

它只证明了一件事：一个以 SYSTEM 身份运行的 Go 程序，可以通过 HTTP 请求驱动虚拟键盘和鼠标。
产品必须具备的东西它一样都没有：

| 缺什么 | 后果 |
| --- | --- |
| 鉴权 | 能连上这个地址的任何人、本机的任何程序、甚至浏览器里的网页，都能在这台机器上打字和点击 |
| 加密 | 走的是明文 HTTP，路上的人能看到也能篡改 |
| 被控端用户的同意和可见提示 | 机器被操作时，坐在机器前的人完全不知情 |
| 会话和授权管理 | 没有"谁在什么时间段被允许操作哪台机器"的概念 |
| 审计记录 | 事后无法知道谁做过什么 |
| 限速和滥用防护 | 可以被无限制地调用 |

另外，它用的是测试签名的驱动和占位的设备编号（厂商号 `0x1234`），这两样都不能用于正式产品。
默认只监听 `127.0.0.1`；改成对外监听，就等于把整台机器的键盘鼠标交给网络上能访问到它的所有人。

## 数据合规风险（写给以后接手的程序员）

以下是工程角度的风险提示，不是法律意见。把这个思路做成产品之前，必须让法务确认。

1. **未经授权的控制。** 没有鉴权意味着任何能连上的人都能操作这台机器。在多数国家和地区，未经授权操作他人的计算机是违法行为。产品必须做到：身份验证、被控端用户明确同意、被控端可以随时中止。
2. **被控端不知情。** 产品必须在被控的机器上有明显、持续可见的提示，说明正在被远程操作，以及是谁在操作。远程会话结束，虚拟设备必须随之移除。
3. **输入的内容本身就是个人数据。** 通过 `/type/文字` 发送的文字出现在网址里，会被浏览器历史、代理、网关和各种访问日志原样记下来，其中可能有密码、证件号、聊天内容。产品不能把输入内容放在网址里，不能记录输入内容，传输必须加密。
4. **日志只记行为，不记内容。** 本程序只记录启动、退出这类事件，不记录请求。产品的审计日志应该记"谁、什么时候、连了哪台机器、做了哪一类操作"，不应该记按了哪些键。
5. **这是整机最高权限的入口。** 虚拟键鼠的输入和真实硬件一样，按 Windows 的机制可以操作管理员权限的窗口、UAC 提示框和锁屏界面（后两项未实测）。所以这个接口必须按最高权限的凭据来保护，不能当成普通的内部接口。
6. **只为兼容，不为隐藏。** 用虚拟设备是因为有些程序不接受软件模拟的输入，不是为了让程序或平台误以为是真人在操作。不要加模仿人手的随机抖动，不要冒用其他厂商的设备编号，不要用它绕过游戏反作弊、风控、验证码之类的检测。这类用途有违约和法律风险。
7. **个人数据保护法规。** 远程操作过程中会接触到被控机器上的个人数据。面向欧盟等地区的用户时会涉及 GDPR 一类的法规（处理的合法依据、数据最小化、跨境传输等），需要法务评估。
8. **测试证书和测试包不得分发。** 驱动目前是测试签名，只能装在测试机上。
9. **容易被安全软件判为远控木马。** "监听网络并注入键盘鼠标输入"正是这类恶意软件的特征。正式产品需要正规代码签名、透明的安装和卸载方式，并和安全厂商沟通。

## 运行

前提：已经用测试包的 `install.cmd` 装好驱动。用管理员身份打开命令行：

```
winuhid-http.exe                         监听 127.0.0.1:8765
winuhid-http.exe -addr 0.0.0.0:8765      允许其他机器访问
winuhid-http.exe -log C:\path\http.log   同时把日志写到文件（没有窗口时用）
```

然后在浏览器地址栏或用 curl 访问，例如 `http://127.0.0.1:8765/mouse/move/800/450`。
访问 `http://127.0.0.1:8765/` 可以看到全部接口。

也可以以 SYSTEM 身份运行（服务、计划任务）。这时程序不在用户的桌面会话里，
它会临时在桌面会话里启动自己的一个副本去读屏幕分辨率和指针位置，不需要你传。

## 接口

| 路径 | 作用 |
| --- | --- |
| `/mouse/move/x/y` | 指针放到主屏幕的像素 (x, y) |
| `/mouse/click/x/y` | 移到 (x, y) 左键单击 |
| `/mouse/dblclick/x/y` | 移到 (x, y) 左键双击 |
| `/mouse/rclick/x/y` | 移到 (x, y) 右键单击 |
| `/mouse/down/x/y`、`/mouse/up/x/y` | 在 (x, y) 按下、松开左键，拖拽用 |
| `/mouse/scroll/n` | 滚轮 n 格，正数向上、负数向下 |
| `/mouse/rel/dx/dy` | 相对当前位置移动，给游戏用 |
| `/key/tap/键名` | 按一下键，支持 `ctrl+c`、`win+r` 这种组合 |
| `/key/down/键名`、`/key/up/键名` | 按住、松开 |
| `/type/文字` | 打一串字，按美式键盘布局，一次最多 256 个字符 |
| `/status` | 当前状态：身份、会话、屏幕分辨率、指针位置 |
| `/quit` | 移除设备并退出 |

键名：`a`-`z`、`0`-`9`、`enter`、`esc`、`tab`、`space`、`backspace`、`delete`、`insert`、`home`、`end`、
`pgup`、`pgdn`、`up`、`down`、`left`、`right`、`f1`-`f12`、`ctrl`、`shift`、`alt`、`win`（以及 `lctrl`、`rctrl` 等），
或者直接写编号，如 `0x28`。

## 返回的状态码

每个请求都一定会有答复，不会一直等。

| 状态码 | 含义 |
| --- | --- |
| 200 | 完成。带坐标的接口还确认过指针确实到了那个位置 |
| 400 | 网址写得不对：坐标不是数字、键名不认识、文字太长 |
| 403 | 输入发出去了但没生效：指针没到指定位置。不判断原因（没接显示器、屏幕被远程桌面接管、锁屏……），这个请求后面的点击不再执行 |
| 500 | 驱动报错或超时、读不到屏幕、或者上一个请求还没结束 |

时限：和驱动的每次交互最多等 2 秒；指针到位最多等 0.4 秒；排队等上一个请求最多 3 秒。
"把指针放到 (x, y)"只发一次，之后只是读位置做确认，不会反复重发。

## 启动和退出

- **启动**：创建键盘、相对鼠标、绝对定位鼠标三个虚拟设备，等约 1.5 秒让系统准备好，再开始接受请求。
- **重复启动**：虚拟设备跟着进程走，所以只有"另一个实例还在运行"才会重复。新实例发现地址被占用时，会让旧实例退出、等它移除设备，再创建自己的。
- **退出**：`/quit`、Ctrl+C、关窗口都会先移除设备再退出。进程被强杀时，系统也会自动收回设备。

## 验证到什么程度

流水线每次构建都会在两台构建机（Windows Server 2022 和 2025）上，分别以管理员身份和 SYSTEM 身份运行这个程序，
并在桌面上开一个测试窗口，确认下面这些真的被窗口收到，而不只是接口返回成功：

- 指针精确到达指定像素；单击、双击、右键、按住和松开；滚轮一格
- 打字 `Hello 123`、组合键 `ctrl+a`、`delete`；按住和松开 Shift
- 网址写错返回 400；输入被系统屏蔽时约 0.4 秒内返回 403，不重试
- 第二个实例启动时接管第一个，设备数量不翻倍；`/quit` 和强杀进程后设备都消失
- SYSTEM 身份、不在桌面会话里时，读到的屏幕分辨率和指针位置与桌面上看到的一致

没有验证过的：

- 多显示器时带坐标的接口对应哪块屏幕；显示缩放不是 100% 的屏幕
- 没接显示器、屏幕被远程桌面接管、锁屏、UAC 提示框出现时的实际表现（按设计应返回 403）
- 桌面版 Windows 上的表现（构建机是服务器版）
- 驱动真的不答复时的超时路径（代码里有时限，但没法在构建机上制造这种情况）

## 已知的限制

- 带坐标的接口对应的是主屏幕。
- 相对移动、滚轮、按键、打字只确认驱动接受了，不确认效果（没有通用的办法读回），所以这几个接口不会返回 403。
- 以管理员身份（不是 SYSTEM）在远程桌面会话里运行时，读不到本机屏幕，带坐标的接口会返回 500。
- 以 SYSTEM 身份运行时，每次带坐标的请求都要到桌面会话里读一次指针位置，比在桌面会话里直接运行慢。
