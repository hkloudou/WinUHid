# WinUHid（可行性验证用的 fork）

这是 [cgutman/WinUHid](https://github.com/cgutman/WinUHid) 的 fork，用来验证一条技术路线：
**用用户态的虚拟 HID 驱动，让一个 Go 程序在 Windows 上驱动虚拟键盘和鼠标。**

验证于 2026-10-03 告一段落。结论：**这条路线可行。**

> **边界：本仓库的产物只用于验证和学习，不是可以发布的产品。**
> 驱动是测试签名，只能装在测试机上；`examples/go-nodll/httpserver` 没有鉴权，不允许分发给用户或部署。
> 详见下面的"边界"一节。

## 结论

| 要回答的问题 | 结论 | 依据 |
| --- | --- | --- |
| 用户态驱动不开"测试模式"能安装吗 | 能 | 仓库所有者在自己的桌面版 Windows 10 上安装成功 |
| 同一个安装包能同时用于 Windows 10 和 11 吗 | 能，包里有两套安装规则，系统自己选 | 流水线：Server 2022 走 Win10 规则，Server 2025 走 Win11 规则 |
| Go 程序能驱动虚拟键鼠吗 | 能 | 流水线：指针移动、按键、点击都确认到达系统 |
| 必须随程序带上游的两个 DLL 吗 | 不必，Go 可以直接和驱动对话 | 流水线：程序放在只有它自己的空目录里运行通过 |
| 能把指针精确放到某个屏幕坐标吗 | 能，用绝对定位的虚拟设备 | 流水线：四个目标位置读回来全部精确到像素 |
| 以 SYSTEM 身份、不在用户桌面会话里，能驱动吗 | 能 | 流水线：以 SYSTEM 身份运行，桌面上的测试窗口收到了点击和打字。仓库所有者在 VMware 里的桌面版 Windows 10 上以 SYSTEM 身份运行，相对移动和按键正常 |
| 能用 HTTP 接口来操作吗 | 能 | 流水线：`/mouse/click/x/y` 这类接口逐项验证 |
| 操作不到的时候会卡死吗 | 不会，有时限，返回 403 或 500 | 流水线：把系统输入屏蔽掉，约 0.4 秒返回 403 |

流水线最近一次的结果：两台构建机各 61 项检查通过、0 项失败。详细报告在 `ci-results` 分支。

## 过程中确认的事实

这些是做产品时用得上的结论，按主题列出。

**安装和签名**

- "测试模式"管的是内核驱动。这个驱动是用户态的，由微软自己的宿主进程加载，不受那条限制。
- 安装时 Windows 查的是"签名用的证书我信不信"。所以测试包要先导入测试证书；换成正式代码签名证书后就不需要这一步。
- 证书不被信任时，安装不是失败，而是 Windows 弹出红色警告"无法验证此驱动程序软件的发布者"并一直等人点。静默安装时表现为卡住。
- GitHub 的构建机默认开着测试模式、没开安全启动，所以"不开测试模式能装"这件事流水线证明不了。
- 上游自带的流水线在现在的 GitHub 构建机上编不过（默认镜像不再带驱动开发套件）。本仓库固定用 `windows-2022` 镜像编译。

**驱动和调用方式**

- 虚拟设备跟着创建它的进程走：进程退出或被强杀，设备自动从系统里消失，不会残留。
- 驱动只允许管理员和 SYSTEM 创建设备，普通权限的程序用不了。
- 上游的 `WinUHid.dll` 很薄，只是打开 `\\.\WinUHid` 并发几条控制命令。对键盘鼠标这种只往系统送输入的设备，Go 标准库就能直接做，见 `examples/go-nodll/vhid`。
- 驱动收到一份输入就交给 Windows 一次，立刻返回，里面没有重试，也不知道"目标坐标"这个概念。
- 新设备创建后要等一小会儿才生效，之前发的输入会丢。

**鼠标**

- 相对移动的量不等于屏幕像素：系统会按指针速度和加速设置放大，而且不是固定倍数。实测发 40 走了 68 像素，发 60 走了 87 像素。
- 要精确定位就用绝对定位的设备：坐标 0 到 32767 表示从屏幕左上到右下，和分辨率无关。
- 只认相对移动的程序（很多游戏）仍然需要相对鼠标，所以两种都保留。

**会话和身份**

- 把参考程序的代码放进自己的程序时，`main` 的第一行必须先处理 `-desktop-info` 这个参数（见 `examples/go-nodll/httpserver/README.md`）。漏掉这一步，SYSTEM 身份下所有带坐标的接口都会返回 500，这个情况实际发生过。

- 虚拟设备的输入进的是"本机屏幕"那个会话，和谁创建的无关。
- SYSTEM 服务读不到用户那边的屏幕分辨率和指针位置，因为每个会话各有一套。参考程序的做法是临时在桌面会话里启动自己的一个副本去读。
- 按 Windows 的机制，Windows 远程桌面会话收不到虚拟设备的输入。这一条没有实测。

**顺带修的上游问题**

- 上游现成鼠标的按键错了一位："按左键"实际按下的是右键。已修（`WinUHidDevs/WinUHidMouse.cpp`），修后实测左键到达的就是左键。

## 没有验证的

- 桌面版 Windows 11
- 不开测试模式的机器上，自检和示例程序是否全部通过（目前只确认了安装成功）
- 多显示器；显示缩放不是 100% 的屏幕
- Windows 远程桌面会话里的表现；UAC 提示框、锁屏界面、Ctrl+Alt+Del
- 开了智能应用控制、S 模式或企业应用白名单的机器
- 带反作弊的游戏是否接受这种虚拟设备
- ARM64
- 正式代码签名（现在全部是测试签名）
- 驱动真的不答复时的超时处理（代码里有 2 秒时限，但没法在构建机上制造这种情况）

## 边界

**这些东西不能直接拿去用：**

- **测试包只能装在测试机上。** 驱动用的是每次构建临时生成的自签名测试证书，不是正式签名。不要发给用户，不要装在生产机器上。
- **`examples/go-nodll/httpserver` 只用于可行性验证和学习，不允许分发给用户或部署。** 它没有鉴权、没有加密、被控端用户不知情、没有审计。能访问到它的人就能在那台机器上打字和点击。
- **示例里的设备编号是占位的**（厂商号 `0x1234`）。正式产品要用自己的编号，不能冒用其他厂商的。
- **虚拟设备是为了兼容，不是为了隐藏。** 不要用它让程序或平台误以为是真人在操作，不要用来绕过反作弊、风控、验证码之类的检测。

**数据合规风险**写在 [`examples/go-nodll/httpserver/README.md`](examples/go-nodll/httpserver/README.md) 里，一共 9 条，接手的程序员必须先读。
那是工程角度的提示，不是法律意见；做成产品前要让法务确认。

**从这里到产品还差：**

- 用公司主体的正式代码签名证书给驱动和程序签名
- 自己的设备编号
- 鉴权、加密、被控端用户的同意和可见提示、会话管理、审计记录
- 远程桌面会话等虚拟设备够不到的场景的替代方案
- 上面"没有验证的"那几项

## 试一下

需要 64 位 Windows 10（2004 及以上）或 Windows 11，管理员权限，测试机。

1. 从 Releases 页的 `dev-test` 下载 `WinUHid-dev-test-kit.zip`，解压。
2. 右键 `install.cmd`，以管理员身份运行。它会先提示这是测试版，按任意键继续。
3. 右键 `selftest.cmd`，以管理员身份运行。指针会自己画个小方框，最后一行是 `RESULT: OK` 即通过。
4. 想试 Go 示例或 HTTP 参考程序，在 `examples\` 目录下，各自有 README。
5. 用完右键 `uninstall.cmd`，以管理员身份运行，卸载驱动并删掉测试证书。

不要通过 Windows 远程桌面连到测试机上跑自检：按 Windows 的机制，那样看不到指针和按键的效果（这一条没有实测）。
